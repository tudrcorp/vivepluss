# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Laravel 12 + Filament 4 admin panel for ViVEplus (an insurance/health-plan affiliation and corporate-quoting platform). Auth/2FA is built on Laravel Fortify, front-end interactivity uses Livewire/Volt, and PDFs (quotes, cards, proposals) are generated with barryvdh/laravel-dompdf. Styling uses Tailwind v4 via Vite.

The product is Spanish-only: navigation labels, form labels, notifications, mail views and PDF documents are written in Spanish, and so are most code comments and commit messages. Keep new strings and comments in Spanish to match; this file and the docblocks are the only English in the repo.

## Commands

- `composer run setup` — first-time bootstrap: `composer install`, copies `.env.example` to `.env`, `key:generate`, `migrate --force`, `npm install`, `npm run build`. Note `.env.example` ships `DB_CONNECTION=sqlite` with the `DB_*` MySQL vars commented out, so a fresh clone has no access to Integracorp's shared schema until they're filled in — only `VIVEPLUS_DB_*` is pre-populated — and that one has to point at a reachable MySQL even for a "sqlite" setup, since ~16 migrations and every quote/catalog model are pinned to `mysql_vivepluss` regardless of `DB_CONNECTION`.
- `composer run dev` — runs the full local dev stack concurrently: `php artisan serve`, `queue:listen`, `php artisan pail` (logs), and `npm run dev` (Vite).
- `npm run dev` / `npm run build` — Vite only. One of the three Vite entries is the Filament panel theme (`resources/css/filament/viveadmin/theme.css`), so **panel styling changes need a rebuild**, not just a reload — see "Panel styling" below.
- `php artisan storage:link` — **not part of `composer run setup`**, but everything user-facing is served off the `public` disk (payment proofs, `documentos-integracorp/{certificados,carnets}`, the quote PDFs under `public/storage/quotes`, the brand logo), so those links 404 on a fresh clone until it's run.
- **Run tests one file at a time**, never the whole suite locally: `./vendor/bin/pest tests/Feature/Auth/AuthenticationTest.php`, or filter by name with `./vendor/bin/pest --filter=<name>`. `composer run test` / a bare `./vendor/bin/pest` runs everything, which is destructive against the local databases — see "Testing setup" below before reaching for it.
- `vendor/bin/pint` — code style fixer (Laravel Pint, no custom `pint.json`, defaults apply). CI runs this on every push/PR to `main`/`develop`.
- `php artisan migrate` — migrations run against the default DB connection (see "Two database connections" below).
- `php artisan catalog:sync-assigned-plans` — rebuilds ViVEplus's local plan/fee catalog from the plans Integracorp assigned to it; scheduled hourly (see "Assigned-plan catalog sync" below). `--white-company=<id>` targets a tenant other than the panel's default.
- `php artisan documents:check-missing` — scans for affiliations/employees whose Integracorp-generated certificate or carnet hasn't arrived within the configured tolerance window; scheduled hourly (see `routes/console.php`), but useful to run manually when diagnosing the webhook flow.

CI (`.github/workflows/tests.yml`, `lint.yml`) runs Pint and the full Pest suite on push/PR to `develop` and `main`.

`livewire/flux` (used in the Fortify auth/settings views under `resources/views/flux/` and `components/auth-*`/`settings/layout.blade.php`) is a paid package hosted on a private Packagist repo — `composer install` will fail without Flux credentials configured (`composer config http-basic.composer.fluxui.dev <username> <license-key>`, as CI does from secrets).

## Architecture

### Two database connections

This app talks to **two separate MySQL databases** via two named connections in `config/database.php`:

- `mysql` (default, env `DB_*`) — Integracorp's shared `operaciones` schema (agencies, agents, affiliations, users, sales, commissions, paid memberships, plus the *legacy* quote tables). Most models use this implicitly.
- `mysql_vivepluss` (env `VIVEPLUS_DB_*`) — ViVEplus's own schema. Models that belong to it set `protected $connection = 'mysql_vivepluss';` explicitly. Currently: the plan catalog (`Plan`, `PlanCondicionado`, `Benefit`, `BenefitPlan`, `Coverage`, `Fee`, `AgeRange`, `Zone`, `DownloadZone`), `Configuration`, and — since the quote cutover described below — every quote model: `IndividualQuote`, `DetailIndividualQuote`, `IndividualQuoteObservation`, `StatusLogInQuote`, `CorporateQuote`, `DetailCorporateQuote`, `CorporateQuoteData`, `CorporateQuoteObservation`, `StatusLogCorpQuote`. `CorporateQuoteRequestObservation` also lives here even though `CorporateQuoteRequest` stayed on `mysql` (no FK; Eloquent hasMany across connections).

When adding a model or writing a query/migration, check which connection the related tables live on — mixing them in one query (e.g. a join) will not work since they're different physical databases. Migrations targeting the second schema declare `protected $connection = 'mysql_vivepluss';` and go through `Schema::connection($this->connection)` / `DB::connection($this->connection)` explicitly (see `2026_08_17_180000_create_vivepluss_individual_quotes_tables.php`); `php artisan migrate` still runs them all in one pass.

**Migrations that touch the default `mysql` connection are a special case**: that schema belongs to Integracorp, this repo's migration history isn't the source of truth for it, and each environment's dump may already contain the table or column. So every such migration is written defensively and idempotently — `if (! Schema::hasTable(...))` / `if (! Schema::hasColumn(...))` guards around the change, no drops, `up()` safe to re-run (`2026_08_12_233000_create_credit_reconciliations_table.php`, `2026_08_10_150000_add_white_company_id_to_...`). **Do not create new tables there at all**: `2026_07_31_030000_create_corporate_quote_request_observations_table.php` was neutered to a no-op once it turned out the table never existed in production, and the table was recreated on `mysql_vivepluss` instead (`2026_08_18_150000_...`). New ViVEplus-owned tables always go on `mysql_vivepluss`; the `mysql` migrations exist only to add nullable columns Integracorp agreed to.

### Quote cutover: legacy Integracorp rows vs. ViVEplus's own

Quotes used to be written straight into Integracorp's `individual_quotes`/`corporate_quotes` on the shared `mysql` database. They now live in ViVEplus-owned tables on `mysql_vivepluss` (created by `2026_08_17_180000_create_vivepluss_individual_quotes_tables.php`, `2026_08_17_180100_create_individual_quote_observations_table.php`, `2026_08_18_120000_create_vivepluss_corporate_quotes_tables.php`, `2026_08_18_120100_create_corporate_quote_observations_table.php`; the legacy tables have no migration in this repo — they come with each environment's dump). Since `affiliations.individual_quote_id` / `affiliation_corporates.corporate_quote_id` already hold ids pointing at legacy rows and no discriminator column was added, **which side an id belongs to is decided by its range**: the new tables start at `AUTO_INCREMENT = 1000001`, far above the legacy maximum, and `IndividualQuote::ID_OFFSET` / `CorporateQuote::ID_OFFSET` (`1_000_000`) mark the boundary.

Consequences for anything touching a quote id:

- **Always resolve stored ids through `App\Support\IndividualQuoteResolver` / `CorporateQuoteResolver`**, never `IndividualQuote::find()` — the id may be legacy. `isLegacy(int $id)` is just `$id < ID_OFFSET`; `find(?int $id)` returns either the `mysql_vivepluss` model or its legacy counterpart. `IndividualQuoteResolver` also carries the two queries that have to branch per side: `coverageOptions($quoteId, $planId)` and `detailSum($quoteId, $planId, $coverageId, $detailIds, $column)` (used by `AffiliationForm`), each running its join inside the right connection so it hits the right `coverages`/`plans` catalog.
- **`App\Models\IntegracorpIndividualQuote`, `IntegracorpCorporateQuote`, `IntegracorpDetailIndividualQuote`** are the read-only mirrors of the legacy tables (default `mysql` connection, same table names as the new ones). Their `booted()` throws `RuntimeException` on `saving`/`deleting` while the connection is `mysql` — deliberately only then, so tests can still write to the throwaway sqlite schema. Follow this same shape (separate model class, write guard) rather than pointing an existing model at the legacy table. This mirrors the `IntegracorpFee`/`IntegracorpAgeRange` split already used by the commission code.
- **`Affiliation::individual_quote` and `AffiliationCorporate::corporate_quote` are accessors, not relations** (`getIndividualQuoteAttribute()` delegating to the resolver). `$affiliation->individual_quote->code` still works, but `with()`, `load()`, `whereHas()` and Filament `->relationship('individual_quote')` do not — and neither would a join, since the two tables sit on different physical databases.
- **The quote `code` is generated by an observer, never by the form.** `App\Observers\IndividualQuoteObserver` / `CorporateQuoteObserver` (registered in `AppServiceProvider::boot()`) fill it on `created()` from the real auto-increment id: `VP-CI-0001` / `VP-CC-0001`, numbered `id - ID_OFFSET`. This replaced a `max('id') + 1` computed in the form defaults, which raced under concurrent creates; `code` is therefore `nullable()->unique()` and the form fields are `disabled()->dehydrated(false)`.
- `AffiliationForm`'s quote picker only lists ViVEplus quotes with `status = 'APROBADA'`; it re-injects an already-linked legacy quote into the options purely so an existing affiliation still renders its name when edited — legacy quotes can no longer be picked, which keeps ViVEplus from writing status back into Integracorp's table.
- Raw-query flows that only ever handle new quotes (`PdfController::generatePdfIndividualQuote`, `UtilsController`'s `createCorporateQuote*` / `storeDetailsIndividualQuote`) use `DB::connection('mysql_vivepluss')->table(...)`.

`tests/Unit/*ResolverIsLegacyTest.php` cover the `ID_OFFSET` boundary as pure unit tests; `tests/Feature/*ResolverTest.php` hand-build a minimal legacy schema on the default (sqlite, per `phpunit.xml`) connection and clean up rows they created on the real `mysql_vivepluss` in `afterEach`.

### Queues: ViVEplus's own `jobs` table

`QUEUE_CONNECTION=database`, and `config/queue.php` resolves the queue's database from `DB_QUEUE_CONNECTION` — **which must stay `mysql_vivepluss`**. The default connection is Integracorp's shared `operaciones` schema, where Integracorp's own worker is already consuming the `default` queue off the same `jobs` table; with both apps pointed there, each worker dequeues and kills the other's jobs (the payload names a class that doesn't exist in its codebase), so queued notifications vanish intermittently with no visible error. `2026_08_18_190000_create_viveplus_queue_tables.php` creates `jobs`/`job_batches`/`failed_jobs` on `mysql_vivepluss`, and `queue.batching`/`queue.failed` follow `DB_QUEUE_CONNECTION` too so failures and batches land in the same schema. Both projects run on one server and the ViVEplus worker is a systemd unit (`queue:work database --queue=default`) — restart it after any deploy, since workers hold config in memory.

Anything the panel dispatches — `PaymentProofUploadedMail`, `AffiliationDocumentAvailableMail`, `WelcomeKitMail`, `SendAffiliationDocumentWhatsApp` — depends on that worker. `AffiliationAutoActivatedMail` is the exception: it goes out with `Mail::to()->send()` inside the request, so it still arrives when the worker is down, which makes it a useful signal when diagnosing "the email never arrived". `sessions` and the `cache` store still live on the shared `operaciones` connection.

### Testing setup

`phpunit.xml` forces `DB_CONNECTION=sqlite` / `DB_DATABASE=:memory:`, and `tests/Pest.php` applies `RefreshDatabase` to `tests/Feature` only. Two consequences before writing a test:

- Only the migrations that live in this repo exist in that sqlite schema. Tables that ship inside each environment's DB dump (`affiliations`, `affiliation_corporates`, the legacy `individual_quotes`) have no migration here, so tests needing them build a minimal version in `beforeEach` — see `tests/Feature/AffiliationDocumentWebhookTest.php` and `tests/Feature/*ResolverTest.php`. SQLite's DDL is transactional, so `RefreshDatabase` rolls those ad-hoc tables back with everything else.
- The override only swaps the *default* connection. Models pinned to `mysql_vivepluss` (every quote model, the plan catalog, `Configuration`) still hit the real local MySQL while tests run — which is why the resolver feature tests delete their own rows in `afterEach`, and why logic that doesn't need a DB is better covered as a pure `tests/Unit` test (`*ResolverIsLegacyTest.php`).

**Never run the full suite on a machine with real data.** `RefreshDatabase` wipes and re-migrates, and ~16 of this repo's migrations declare `protected $connection = 'mysql_vivepluss'` — those run against the real `vivepluss_db` regardless of the sqlite override, `down()` included (`2026_08_18_190000_create_viveplus_queue_tables.php` drops `jobs`/`job_batches`/`failed_jobs`). The `mysql` connection points at Integracorp's shared `operaciones`, which is the same physical database their production-shaped local dump lives in. Run the file you're working on, not `composer run test`.

Note what CI actually is: `tests.yml` copies `.env.example`, runs `npm run build` and then `./vendor/bin/pest` — **with no MySQL service provisioned**, so `mysql_vivepluss` has no database there either. A new test that reaches that connection is a test that can only pass on a developer machine; keep new coverage either in pure `tests/Unit` or on the sqlite default connection.

### Filament resource layout (v4 style)

Admin UI lives under `app/Filament/Resources/<Name>/` using Filament 4's split-file convention rather than single-class resources:

```
Resources/<Name>/
  <Name>Resource.php          # resource definition, navigation, relations registration
  Pages/                      # List/Create/Edit page classes
  Schemas/<Name>Form.php      # form schema (create/edit)
  Tables/<Name>Table.php      # table columns/filters/actions
  RelationManagers/           # nested relation managers, when present
```

Follow this same split when adding a new resource rather than inlining `form()`/`table()` on the resource class. The single Filament panel is registered in `app/Providers/Filament/ViveadminPanelProvider.php` (id `viveadmin`, path `/viveadmin`), which auto-discovers resources/pages/widgets from their respective directories and defines panel-wide config (theme colors pulled from the `Configuration` model, navigation groups, user menu actions, etc.).

Resources can register extra pages beyond the default index/create/edit trio in `getPages()` — e.g. `AffiliationResource`'s `affiliates` route (`Pages/ManageAffiliates.php`, a `ManageRelatedRecords` page) manages an affiliation's family members, and `AffiliationCorporateResource`'s analogous `Pages/ManageAffiliateCorporates.php` manages a corporate affiliation's employees. Standalone pages that aren't tied to a resource (e.g. `App\Filament\Pages\EstructuraViveplus`, an org-hierarchy viewer, and `CondicionadosPorPlan`, see below) set `$shouldRegisterNavigation = false` and are instead linked from `userMenuItems()` in the panel provider, gated by `Auth::user()->is_whiteCompanyAdmin` / `agency_type === 'MASTER'`.

List pages override `getHeader(): ?View` to return a `resources/views/filament/resources/<resource>/list-header.blade.php` partial (icon + title + description) in place of Filament's default header — follow this convention for new list pages rather than relying on `$title` alone.

Filament 4's API differs from v3 in ways that will silently mislead v3-shaped code: form schemas are `Filament\Schemas\Schema` (`public static function form(Schema $schema): Schema`), not `Filament\Forms\Form`; **layout** components (`Section`, `Grid`, `Fieldset`, `Tabs`) come from `Filament\Schemas\Components\*` while **field** components (`TextInput`, `Select`, `FileUpload`) stay in `Filament\Forms\Components\*`; navigation icons are the `Filament\Support\Icons\Heroicon` enum (`protected static string|BackedEnum|null $navigationIcon`) and `$navigationGroup` is `string|UnitEnum|null`. Resource-level visibility is gated by overriding `shouldRegisterNavigation()` against `Auth::user()?->is_whiteCompanyAdmin` / `agency_type == 'MASTER'`, the same check used for the standalone pages.

Internal observations (the administrative note trail on affiliations, quotes and corporate quote requests) are not re-implemented per resource: `App\Support\Filament\InternalObservations::formSchema()` builds the single `description` textarea and `::store($record, $relationship, $data)` writes the row with `created_by` plus the success notification. Both the `RelationManagers/ObservationsRelationManager.php` of each resource and the equivalent table action call it — reuse it rather than duplicating the form/notification pair.

### Panel-wide config every resource inherits

`ViveadminPanelProvider` sets a handful of panel-level options that change how a *new* resource behaves before it writes a line of its own:

- `->resourceCreatePageRedirect('index')` / `->resourceEditPageRedirect('index')` — Create and Edit always bounce back to the list, so don't hand-roll `getRedirectUrl()` to reproduce it, and don't expect to land on the edit page after creating.
- `->databaseTransactions()` — Filament wraps action/page saves in a transaction on the **default** connection. Since most of this app's own data lives on `mysql_vivepluss`, those writes are *not* covered by that rollback; an action that touches both databases has to handle its own consistency.
- `->navigationGroups([...])` fixes the sidebar order (`INDIVIDUALES`, `CORPORATIVAS`, `ORGANIZACION`, `ZONA DE DESCARGA`) — a resource whose `$navigationGroup` isn't one of those still renders, just outside the intended order. Reuse an existing group name unless a new section is really wanted.
- `->spa()` (Livewire SPA navigation), `->breadcrumbs(false)`, `->maxContentWidth(Width::Full)`, `->databaseNotifications()`, `->font('Quicksand')`.
- Theme colors come from `Configuration::findOrFail(1)` — **hardcoded id 1**, not `currentWhiteCompanyId()`, so a database whose `configurations` table has no row 1 takes down every panel page. The `edit_configuration` user-menu action right below it resolves by `white_company_id` with a fallback instead; prefer that shape for new lookups.

### Panel styling (custom Filament theme)

The panel's look is a custom Filament theme at `resources/css/filament/viveadmin/theme.css` (registered with `->viteTheme(...)`, which is why it's a Vite entry and needs `npm run build`/`npm run dev`), plus `resources/css/filament/download-zone-tabs.css` imported from it. Its `@source` globs cover `app/Filament/**` and `resources/views/filament/**`, so Tailwind classes written inside PHP schema/table files are picked up.

Two conventions live there rather than in component code: `.ios-action-btn` (pill-shaped header buttons with press feedback) is applied through `->extraAttributes(['class' => 'ios-action-btn'])` on the header actions of every `List*` page — reuse it instead of restyling per resource; and below `lg` the sidebar is restyled into a bottom sheet, so any change to navigation chrome has to be checked at mobile width too.

### `app/Http/Controllers` is mostly dead code

`routes/web.php` registers **no controller routes at all** — only `/`, `/external` (logout), the Volt auth/settings pages and the three public Volt agent/agency creation forms; `routes/api.php` has the two Integracorp endpoints described below. Everything else in this app is the Filament panel.

The ~64 classes in `app/Http/Controllers` are inherited wholesale from Integracorp's own Laravel app (medical histories, inventory, providers, travel agencies…) and are unreachable. The handful that *are* live are used as plain service classes, invoked statically or via `new` from Filament schemas/tables/pages: `UtilsController` (quote creation/recalculation, by far the most used), `AffiliationController` / `AffiliationCorporateController` (`uploadPayment` and friends), `PdfController`, `IndividualQuoteController` / `CorporateQuoteController` (called only from `UtilsController` to render the per-tier proposal PDFs), `NotificationController`, `LogController`, and `MiddlewareController` (called from the `DuplicatedSession` middleware).

Two consequences: put new logic in `app/Support` or `app/Services` rather than growing this directory, and **don't trust a bare grep to tell you whether something is used** — the dead controllers still reference nearly every model and job in the app, so a class with "references" may in fact have zero live callers. Check whether the referencing file is one of the live controllers above.

### Domain model shape

Core business entities and how they relate:
- **Agencies/Agents** (`Agency`, `Agent`, `AgencyType`, `AgentType`) — the sales org structure; agencies can be "MASTER" type. Agent/agency creation flows are exposed as public Volt routes (`/agency/c/{code?}`, `/agent/c/{code?}`, `/m/o/c/{code?}` in `routes/web.php`), separate from the Filament panel.
- **Quotes**: `IndividualQuote` and `CorporateQuote` (plus `Detail*Quote`, `CorporateQuoteData`, `*QuoteObservation`, `StatusLog*Quote` for history/audit trails) — all on `mysql_vivepluss` since the cutover described above, while `CorporateQuoteRequest` stayed on `mysql`, which is why `corporate_quotes.corporate_quote_request_id` and `corporate_quote_request_observations.corporate_quote_request_id` carry no FK. The request observations table is ViVEplus-owned (`mysql_vivepluss`); it was never created on Integracorp. Corporate quotes have plan tiers (Inicial/Ideal/Especial) — see `App\Actions\Contraportada*`/`Planes*`/`Portada*` classes used to build PDF proposal documents, and `App\Jobs\SendEmailPropuestaEconomica*` jobs that render and email those proposals per plan tier.
- **Affiliations**: `Affiliation`/`AffiliationCorporate` plus supporting `*Observation`, `*Document`, `StatusLogAffiliation*` models — the enrollment records once a quote converts.
- **Plan catalog** (on the `mysql_vivepluss` connection): `Plan`, `PlanCondicionado`, `Benefit`, `BenefitPlan`, `Coverage`, `Fee`, `AgeRange`, `Zone`.
- **Configuration** — single-row(ish) tenant/branding config (colors, logo, currency symbol, social URLs) read directly by the panel provider and views; look here before hardcoding branding values.

### Sales-force hierarchy (`AgencyHierarchy`)

Who reports to whom is stored in **text columns, not foreign keys**: an agency carries its parent's code in `agencies.owner_code` (a MASTER points at itself — `TDG-194`'s `owner_code` is `TDG-194`, which is what used to make the old `where('owner_code', $user->code_agency)` filters appear to work), an agent or sub-agent carries the code of the agency it hangs off in `agents.owner_code`, and a sub-agent additionally points at its responsible agent through `agents.owner_agent`. `agency_types` only has 1 = MASTER and 3 = GENERAL; `agent_types` has 1 = AGENCIA GENERAL, 2 = AGENTE, 3 = SUB-AGENTE. The user row that represents an agency is created when it's activated (`AgenciesTable`): `code_agency` is that agency's own code and `agency_type` is `'MASTER'` or `'GENERAL'`.

`App\Support\SalesForce\AgencyHierarchy` is the single place that resolves scope from that shape — use it instead of comparing `owner_code` to `Auth::user()->code_agency` by hand:

- `isMaster()` (white-company admin or `agency_type === 'MASTER'`) / `isGeneral()`, and `canManageAgents()`, which also honours `Configuration::agents_module_enabled`. **General agencies manage agents too**, only within their own branch — `AgentResource` gates `shouldRegisterNavigation()`/`canAccess()`/`canCreate()` on this, so the resource is no longer MASTER-only.
- `visibleAgencyCodes()` — a MASTER sees its own code plus every general agency hanging off it, a general agency only its own. `AgentsTable` filters `whereIn('owner_code', …)` with it, which is what lets a MASTER finally see the agents of its general agencies (and sub-agents too, since those also carry `owner_code`). The structure is two levels deep, so one hop is enough.
- `assignableAgencyOptions(?string $codigoActual)` — the "Jerarquia" select in `AgentForm`. It includes **the user's own agency**, which the old query left out; passing the record's current `owner_code` re-injects an inactive or out-of-scope value while editing, so saving can't silently null it out and drop the agent off the tree. Same re-injection idea as `AffiliationForm`'s legacy-quote option.

`EstructuraViveplus` (the org-tree page) predates the helper and still walks the same columns inline; it stays MASTER-only.

### White-label scoping (`white_company_id`)

Several `mysql`-connection tables (`sales`, `collections`, `paid_memberships`, `agencies`, `agents`, plus the `affiliations`/`affiliation_corporates` queried by the dashboard widgets) and the `mysql_vivepluss` `individual_quotes`/`corporate_quotes` carry a `white_company_id` column that ties a row to a tenant/brand row in the `mysql_vivepluss` `configurations` table. `Configuration::currentWhiteCompanyId()` resolves the active scope from the authenticated user's `white_company_id`, falling back to the first configured tenant. Use this helper (rather than hardcoding a tenant id) whenever a query, widget, or PDF needs to filter or brand by the current white-label company — it's the pattern already used by `VentasChart`/`VentasPorPlanChart`/`StatsOverview` and by the quote PDF builders below. `App\Models\WhiteCompany` (no explicit `$connection`, so it lives on `mysql` — a *different* connection than `Configuration` despite sharing the same `white_company_id` value) holds per-tenant billing info such as `assigned_credit`, read by `StatsOverview::getAssignedCredit()`.

### PDF/document generation

Controllers (`IndividualQuoteController`, `CorporateQuoteController`, `AffiliationController`, `PdfController`) build PDFs directly with `Barryvdh\DomPDF\Facade\Pdf::loadView(...)` against Blade views in `resources/views/documents/` (e.g. `propuesta-economica.blade.php`, `propuesta-economica-cor.blade.php`, `propuesta-economica-multiple.blade.php`, `certificate.blade.php`). Small `App\Livewire\{Portada,Contraportada,PlanesCotizacion}*` components render the cover-page/plan-tier partials embedded inside those documents. Generated quote PDFs are saved under `public/storage/quotes` and then emailed via `App\Mail\SendMail*` mailables or dispatched through `App\Jobs\SendEmailPropuestaEconomica{Inicial,Ideal,Especial}Cor` (one per corporate plan tier) / `SendEmailPropuestaEconomicaMultiple` jobs.

Individual quotes go through `App\Services\IndividualQuotePdfBuilder` instead of a direct `Pdf::loadView()` call: if the current white-label `Configuration` has `quote_cover_individual`/`quote_back_cover_individual` template files set, it merges those single-page PDFs with a dompdf-rendered calculations page via `setasign/fpdi`, matching the generated page size (converted mm→pt) to the uploaded templates. It falls back to the full `documents.propuesta-economica` dompdf render if no templates are configured or the FPDI merge throws. Apply this same builder-with-fallback shape if corporate quotes need per-tenant cover templates later.

Plans that arrive through the assigned-plan sync get the **generic** proposal instead of a hand-written one: `IndividualQuoteController::generatePdfPlanAsignado()` / `CorporateQuoteController::generatePdfPlanAsignado()` (called from `UtilsController` behind the same `QuotablePlans::usesGenericRepeater()` branch the forms use) render through `App\Livewire\PlanesCotizacion{Individual,Corporativa}Asignado`, which build the rate table's coverage columns from the plan's own `Coverage` rows ordered by price and place each cell by matching `coverage_id` rather than trusting row order. The `PlanesCotizacion*{Inicial,Ideal,Especial}` components exist only for the three legacy plans — a newly assigned plan needs no new component.

### Affiliation payment/activation flow

`AffiliationController::uploadPayment` (and its bulk counterpart `uploadPaymentMultipleAffiliations`) is the entry point when an analyst uploads a payment proof for an affiliation; it creates a `PaidMembership` row per method/frequency combination but only auto-approves/activates for `payment_method === 'CREDITO'` — every other method leaves the proof `PENDIENTE` with the affiliation untouched, since validating the proof, approving it, generating the next due dates, and activating the affiliation is done by Integracorp's own analysts outside ViVEplus, not by the ViVEplus analyst who uploaded it. `approveAndActivate()` (called only for `CREDITO`) marks the proof `APROBADO` and activates the affiliation immediately (`status = 'ACTIVA'`, `activated_at`/`effective_date` set), then calls `createUpcomingCollections()` to pre-generate the rest of the annual cycle's pending `collections` rows (per `payment_frequency`: MENSUAL → 11 more, TRIMESTRAL → 3, SEMESTRAL/ANUAL → 1) and emails `AffiliationAutoActivatedMail` to `config('parametros.ACTIVATION_NOTIFICATION_EMAILS[_DEV]')`. A failed notification email is logged but never rolls back the activation. `App\Http\Controllers\PaidMembershipController::approvePayment`/`PaidMembershipCorporateController::approvePayment` implement an older manual-approval flow (status update, `Sale`/`Collection` creation, `SendAvisoDePago`/`CreateAvisoDeCobro` jobs) but aren't wired to any route or Filament action — dead code from before the CREDITO auto-approval was added, not the mechanism Integracorp uses today. Payment-proof file fields (`document_usd`, `document_ves`, `Configuration::brandLogo`) are inconsistently stored across the `local`/`public` disks depending on how each `FileUpload` component was declared — when resolving one of these to an absolute path, check both disks (see `resolveLogoPath`/`resolvePaymentDocumentPaths`) rather than assuming one.

Both upload flows finish by rewriting `document_usd`/`document_ves` through `AffiliationController::publicDocumentUrl()`, which turns Filament's relative path into ViVEplus's absolute public URL — the same reasoning as `generateCreditNote()`: Integracorp shares this database but not the file storage, so a relative path would 404 from their panel. Every `document_usd` upload in `AffiliationsTable` now declares `->disk('public')` for that URL to resolve (they used to default to `local`). The helper is a no-op on blank/`'N/A'`/already-absolute values and returns the path untouched when the file isn't on the `public` disk, so it can't fabricate a broken link; **no backfill was done**, so rows created before this change still hold relative paths — which is why `resolvePaymentDocumentPaths()` still has to handle both shapes.

Both upload entry points end by calling `notifyPaymentProofUploaded()`, for **every** payment method (not just `CREDITO`). It mirrors the document-webhook notification shape: gated per white-label by `Configuration::payment_notifications_enabled`, fanning out to `payment_notification_emails` (queued `App\Mail\PaymentProofUploadedMail`, view `resources/views/mails/comprobante-cargado.blade.php`) and `payment_notification_phones` (reusing the `SendAffiliationDocumentWhatsApp` job, attaching whatever `resolvePaymentDocumentPaths()` found, or sending text only when there are no files). The wording says "Nota de crédito" vs "Comprobante de pago" depending on `payment_method === 'CREDITO'`. Failures are caught and logged only, never affecting the payment itself.

### White-label credit ledger (`CreditReconciliation`)

The `CREDITO` payment method on `AffiliationController::uploadPayment` lets an affiliation be paid against the white-label company's line of credit instead of a real proof of payment: it generates a credit-note PDF (`documents/nota-credito.blade.php`, via `generateCreditNote()`), stores it as the `PaidMembership`'s `document_ves` with `status = 'APROBADO'` immediately, and records the movement with `recordCreditMovement()` as a row in `credit_reconciliations` (`mysql` connection, model `App\Models\CreditReconciliation`). `CreditReconciliation::remainingCredit($whiteCompanyId)` computes `WhiteCompany::assigned_credit` minus the sum of `total_to_pay` across that tenant's ledger rows — this is the single source of truth for "how much credit does this white-label company have left," checked before allowing a `CREDITO` payment (`AffiliationsTable.php`) and surfaced on `StatsOverview`. There's no FK between `paid_memberships`/`collections` and `credit_reconciliations`; rows link back via `collection_invoice_number`/`paid_membership_id`.

### Sale/commission registration on Integracorp's shared tables

ViVEplus's default `mysql` connection and Integracorp's own app point at the *same physical database* (`operaciones`) — `sales`, `commissions`, `white_companies`, `white_company_fees`, and Integracorp's own plan/coverage/fee/age-range catalog all already live there alongside `affiliations`/`paid_memberships`. On the first `CREDITO` payment of an affiliation (inside `AffiliationController::approveAndActivate()`, gated the same way as `createUpcomingCollections()` so it only runs once per affiliation, not on every subsequent installment), `registerSaleAndCommission()` writes a `Sale` and a `Commission` row exactly like Integracorp's own `PaidMembershipController::approvePayment()` does for an allied/white-label company — ViVEplus is always the allied party from Integracorp's point of view, so only that code path is ported (not the agent/sub-agent/agency commission tree, which is Integracorp's own direct-sales channel).

The amount used for `Sale.total_amount` and for the commission is **not** the analyst-entered `total_amount` (that still drives `PaidMembership`/`Collection`/`CreditReconciliation` unchanged) — it's the negotiated *neta* resolved by `App\Support\WhiteCompanies\WhiteCompanyNegotiatedRateResolver::settlementForAffiliation()`, which sums per-person (titular and/or each `Affiliate`) `sale_price`/`neta` from `WhiteCompanyFee` (keyed by `white_company_id` + `fee_id`) after resolving the matching `fee_id` by plan+coverage+age against **Integracorp's own fee catalog** (`App\Models\IntegracorpFee`/`IntegracorpAgeRange`, table names `fees`/`age_ranges`; the plan of a fee comes from `fees.plan_id`, a column added on 2026-08-18 — before that it was deduced through `age_ranges.plan_id`, so don't reintroduce that path — deliberately separate model classes from ViVEplus's own `mysql_vivepluss`-connection `Fee`/`AgeRange`, since `white_company_fees.fee_id` references Integracorp's catalog, not ViVEplus's, even though the two catalogs happen to mirror IDs for the plans ViVEplus sells). The resolved settlement is snapshotted onto `Affiliation.white_company_sale_price`/`white_company_neta`/`white_company_fee_id` the first time (these columns already exist on the shared `affiliations` table from Integracorp's side) so later installments reuse the same figures instead of recomputing. `WhiteCompanyPaymentSettlement::installmentNeta()`/`installmentMasterCommission()` divide the annual neta/margin (`sale_price - neta`) by the payment-frequency period count for the per-installment `Sale`/`Commission` amounts — all of the commission goes to `commission_agency_master_usd` (Integracorp's cut), with the agent/sub-agent/agency-general fields left at zero.

If no `WhiteCompanyFee` row matches a person's resolved fee, `WhiteCompanyNegotiatedRateResolver` throws `App\Exceptions\WhiteCompanyNegotiatedRateMissingException` **before any write happens** (it runs at the very top of the `CREDITO` branch, ahead of the credit note/`PaidMembership`/`CreditReconciliation`) in both `uploadPayment()` and `uploadPaymentMultipleAffiliations()`, so a missing rate blocks the whole approval cleanly instead of leaving it half-done. That exception (like any other now) propagates out of `uploadPayment()` — its catch block used to `dd()` on `\Throwable` before logging/notifying, which silently swallowed every exception behind a debug dump; that `dd()` was removed so failures reach the existing `Log::error()` + `Notification::make()->danger()` and actually show the analyst a clear message. The bulk counterpart carried the same `dd($th);` until it was removed too, so both flows now fail through to the log plus the analyst-facing notification.

### Assigned-plan catalog sync (Integracorp → ViVEplus)

ViVEplus quotes against **its own** catalog on `mysql_vivepluss` (`Plan`, `Coverage`, `Fee`, `AgeRange`), which is a copy of the Integracorp plans it resells, under its own commercial names (PLAN ESENCIAL / BIENESTAR / PREMIUM ↔ Integracorp's INICIAL / IDEAL / ESPECIAL, same ids). **The price in that local catalog is the negotiated `white_company_fees.sale_price`, not Integracorp's list price** — fee 1 is 180.00 locally and 160.00 in Integracorp's `fees`.

That copy used to be maintained by hand and had already drifted. `App\Support\Catalog\AssignedPlanCatalogSync` (Artisan `catalog:sync-assigned-plans`, scheduled hourly in `routes/console.php`) rebuilds it from the **two-step assignment an Integracorp analyst performs**, mirroring that split exactly:

1. **`white_company_plans`** — which plans the partner may quote. A plan can't be assigned there without benefits. This is what the sync iterates; the plan and its benefits come from here.
2. **`white_company_fees`** — the negotiated sale price per fee. Only fees with a row here are synced, and `sale_price` becomes `fees.price`.

So an assigned plan with no negotiated rates lands in the catalog with its benefits but is **not offered for quoting** — `Plan::scopeCotizable()` (`type = BASICO` + active + `whereHas('fees')`) is what both quote forms and `UtilsController` use instead of `where('type','BASICO')`, and the sync only creates local fees for what has a rate. Read-only mirrors of Integracorp's catalog (`IntegracorpPlan`, `IntegracorpCoverage`, `IntegracorpFee`, `IntegracorpAgeRange`, `IntegracorpBenefit`, `IntegracorpBenefitPlan`, `IntegracorpWhiteCompanyPlan`, `IntegracorpWhiteCompanyPlanLabel`) all sit on the default `mysql` connection, so tests can stand them up in sqlite.

What it deliberately does **not** do: overwrite the name of a plan ViVEplus already has (only plans it creates get named, from `white_company_plan_labels` or the Integracorp description); delete benefits (it only adds missing ones); touch condicionados; or sync a plan that isn't assigned, however many rates it has.

Three traps this code exists to avoid, all verified against real data:

- **`age_ranges` ids do not mirror between the two databases** (id 24 is "12 a 50" of plan 5 in ViVEplus and "0 A 75" of plan 16 in Integracorp), so the sync treats Integracorp's id as a preference only: it reuses it when free or equivalent, otherwise finds an equivalent range in the plan or creates a new one. `fees` ids *do* mirror (37/37 verified) and are the key `white_company_fees.fee_id` relies on, but the sync still refuses to overwrite a local fee whose plan/coverage differ, reporting it instead.
- **`benefits` ids don't mirror either** (id 20 is "VIDA" in ViVEplus and "ASISTENCIA MÉDICA POR ACCIDENTES" in Integracorp), so benefits are matched **by description**, reusing the local row when it matches.
- Plans arrive with Integracorp's `type` (e.g. `DRESS-TAILOR`); the sync forces `BASICO`, because that's what ViVEplus's quote forms list.

### Quote forms: three hand-written plans plus everything the sync brings in (`QuotablePlans`)

The consumer side of that catalog. The two quote forms (`IndividualQuoteForm`/`CorporateQuoteForm` plus their `Create*` pages) and `UtilsController` all go through `App\Support\Catalog\QuotablePlans` rather than hardcoding plan ids or names:

- The three historical plans (`LEGACY_PLAN_IDS = [1, 2, 3]` — Esencial/Bienestar/Premium) each have their own hand-written age-range repeater in the form. Any other plan — i.e. whatever Integracorp assigns and `AssignedPlanCatalogSync` brings in — takes the **generic repeater**, built from the chosen plan's own ranges; `usesGenericRepeater()` is the branch, and `withPlanId()` stamps `plan_id` onto its rows since the generic repeater doesn't carry a plan field (the plan was picked a step earlier). Without this, selecting an assigned plan left the age step empty and the quote couldn't be completed.
- `MULTIPLE = 'CM'` is the sentinel value for "cotización múltiple" stored in the `plan` column — not a plan id. Anything reading a quote's `plan` has to handle it; `quoteLabel()` is what the tables use so a column doesn't come up empty for a plan that isn't in any hand-written list.
- `ageRangeOptions()`/`ageDescription()` only offer ranges that actually have a `Fee`. The local catalog drags along ranges from plans that never existed (plan 16's "90 A 100" had no rate at all), and offering one produced a priceless, silently empty quote.
- `coverageLabel()` renders a coverage amount the way the hand-written proposals spell it (1000 → "1K"), so an assigned plan's PDF reads like the historical ones.

### Zona de descarga (`Zone` / `DownloadZone`)

`DownloadZoneResource` (navigation group "ZONA DE DESCARGA", model `DownloadZone` on `mysql_vivepluss`) is the document library agents download from: each row is a file belonging to a `Zone`, ordered by `position`. Its list page is tab-per-zone rather than a plain table — `HasDownloadZoneTabsGridLayout` overrides `getTabsContentComponent()` to render the tabs as an uncontained grid (`fi-download-zone-tabs-grid`), and `DownloadZoneTabIcons` picks each tab's `Heroicon` by matching the zone's name/code, so a new zone gets a sensible icon without a mapping table. Reordering is a header action (`editOrder`) that writes `position` for the active tab's zone. Unlike the resources gated in `shouldRegisterNavigation()`, this one is visible to everyone and instead gates *writes* through `DownloadZoneResource::canManage()` (`is_whiteCompanyAdmin` / `agency_type === 'MASTER'`) wired into `canCreate`/`canEdit`/`canDelete` — follow that shape when a resource should be readable by agents but editable only by admins.

### Integracorp document webhook (certificates/carnets)

ViVEplus no longer generates the affiliation certificate (`certificado`) or member card (`carnet`) itself — Integracorp generates them externally when an operator runs "Regenerar documentos" and pushes the resulting PDF to `POST /api/documents/webhook` (`routes/api.php`, registered via `withRouting(api: ...)` in `bootstrap/app.php` — Laravel 12 has no `api.php` by default, so this is the only API route file in the app; `App\Http\Controllers\Api\AffiliationDocumentWebhookController`). The route is protected by `App\Http\Middleware\VerifyIntegracorpDocumentWebhook`: a fixed Bearer token (`parametros.INTEGRACORP_WEBHOOK_TOKEN`) plus an HMAC-SHA256 signature (`parametros.INTEGRACORP_WEBHOOK_SECRET`) over a canonical string of the payload fields (not the raw multipart body). The controller is idempotent on `idempotency_key` and rejects stale deliveries by comparing `generated_at`, writes the file atomically (temp file + `Storage::move`) under `documentos-integracorp/{certificados,carnets}` on the `public` disk, and upserts an `App\Models\AffiliationDocument` row (table `affiliation_integracorp_documents`) keyed on `affiliation_code` + `document_type` + `affiliate_identification` (blank for `certificado`, since it's one per affiliation; populated for `carnet`, since it's one per family member/employee). `AffiliationDocument::latestFor()` is how the panel resolves the current file to offer for download. The `documents:check-missing` Artisan command (scheduled hourly in `routes/console.php`) logs affiliations/employees whose certificate or carnet hasn't arrived within `parametros.DOCUMENT_SYNC_ALERT_HOURS` (default 48h) of the affiliation being created.

After storing each document, `notifyAnalysts()` fires one notification per document received (it doesn't wait for the certificate and all carnets of an affiliation to arrive) — gated per white-label by `Configuration::document_notifications_enabled`, fanning out to `document_notification_emails` (via `AffiliationDocumentAvailableMail`) and `document_notification_phones` (via the `SendAffiliationDocumentWhatsApp` job). That job posts to the ultramsg.com API using the same curl pattern as `MiddlewareController::notificacionSesionDuplicada` — the only WhatsApp send in this codebase that actually works; other flows reference a job class from `NotificationController` that doesn't exist. Notification failures are caught and logged inside `notifyAnalysts()` so they never affect the 201 already returned to Integracorp.

### Integracorp stats endpoint (the other direction)

`routes/api.php` holds a second route pointing the opposite way: `GET /api/stats/individual-quotes` (`App\Http\Controllers\Api\IndividualQuoteStatsController`), which Integracorp polls to keep counting ViVEplus's individual quotes now that those rows no longer land in its own database (see the quote cutover above). It cursor-paginates `IndividualQuote` on `mysql_vivepluss` (`per_page`, default 100) ordered by id and returns a deliberately PII-free projection — `id`, `code`, `status`, `plan`, `code_agency`, `owner_code`, `white_company_id`, `created_at`, no name/email/phone. Legacy quotes are not included, since Integracorp reads those from its own tables.

Auth is `App\Http\Middleware\VerifyIntegracorpStatsApiToken`: a fixed Bearer token `hash_equals`'d against `parametros.INTEGRACORP_STATS_API_TOKEN` (a separate secret from `INTEGRACORP_WEBHOOK_TOKEN`/`_SECRET`, which guard the inbound webhook), plus `throttle:60,1`. There is no HMAC here on purpose — nothing is being written, so there is no payload whose integrity needs verifying. A missing configured token returns 500 rather than silently accepting; a bad token returns 401, and both cases (plus successes) are logged with the caller's IP.

### Affiliation welcome kit & branded transactional mail

`App\Support\AffiliationWelcomeKit` assembles the "Kit de Bienvenida" for an individual affiliation from three sources that already live on disk, without persisting anything new: the Integracorp-delivered certificate and each affiliate's carnet (`AffiliationDocument`, see the webhook section below) plus the plan's condicionado PDF (`PlanCondicionado`, `mysql_vivepluss` connection, uploaded per-plan by a white-company admin/MASTER agency user via the standalone `CondicionadosPorPlan` page — there's no full `Plan` CRUD in this panel, so that page only exposes the PDF upload). `isReadyFor()` gates the panel action's visibility on the certificate plus *all* carnets being present; a missing condicionado doesn't hide the action, since that gap is a configuration issue rather than something Integracorp owes. `collect()` returns the individual files with warnings for anything missing (used for email/WhatsApp, sent as separate attachments/messages), and `build()` zips them on the fly into `storage/app/welcome-kits` for direct download from `AffiliationsTable`. `WelcomeKitMail` (a queued `Mailable`, `resources/views/mails/kit-bienvenida.blade.php`) sends `collect()`'s files as attachments.

`App\Support\Mail\MailBranding::forWhiteCompany()` resolves a tenant's logo (checking both `public`/`local` disks — the same ambiguity as `AffiliationController::resolveLogoPath`) and primary color from `Configuration`, for any `Mailable` rendering the shared `resources/views/components/mail/layout.blade.php` component; `WelcomeKitMail` and `SalesForceActivatedMail` both use it instead of duplicating the lookup. `App\Support\SalesForceActivation::notify()` is the shared email+WhatsApp notification (with the default password) fired when an agent or agency is activated in the sales force, called identically from `AgenciesTable` and `AgentsTable`.

### App-specific config (`config/parametros.php`)

Integration constants live in `config/parametros.php` instead of `env()` calls scattered at the call site: the logout redirect URLs, the ultramsg WhatsApp endpoint URLs and token (hardcoded there, not env-driven), the Integracorp webhook/stats secrets (`env()`-backed, blank in `.env.example`) and `DOCUMENT_SYNC_ALERT_HOURS`. Notification recipient lists follow a prod/dev split convention: `ACTIVATION_NOTIFICATION_EMAILS` is assembled from the `MAIL_ACTIVATION_NOTIFY_*` vars (commented out in `.env.example`, filled only in production) while `ACTIVATION_NOTIFICATION_EMAILS_DEV` holds the single developer address, and callers choose between them with `app()->environment('production')` so local/staging runs never mail administración/negocios. Add new integration constants in this shape rather than reading `env()` directly.

### Auth

Fortify-based auth with two-factor support (`app/Actions/Fortify`), plus a custom `DuplicatedSession` middleware applied to the Filament panel to prevent concurrent sessions. Logout redirects to an external URL (`config('parametros.REDIRECT_LOGOUT_EXTERNAL_URL')`) via the `/external` route, which also invalidates the Filament guard/session.

### Dashboard widgets

`app/Filament/Widgets/` holds the panel dashboard: `StatsOverview` (a plain `Widget`, not `StatsOverviewWidget`, rendering its own Blade view at `resources/views/filament/widgets/stats-overview.blade.php`) plus two `ChartWidget` subclasses — `VentasChart` (monthly individual-vs-corporate sales totals) and `VentasPorPlanChart` (monthly sales broken out per plan) — that query `affiliations`/`affiliation_corporates` via `DB::` raw queries, scoped by `Configuration::currentWhiteCompanyId()`, with chart currency formatting from `Configuration::currencySymbol()`. `StatsOverview` builds its own per-metric sparklines (`buildSparkline()`, hand-rolled SVG path + per-point hover coordinates, no charting library) and month-over-month deltas (`monthOverMonth()`/`changeSummary()`) for agencies/agents/quotes counts, all scoped by `white_company_id`. Widgets are auto-discovered by the panel provider like resources/pages.
